## 1. Security, cryptography and compliance

The items below are outstanding verification work, not confirmed vulnerabilities. Provider-dependent checks require the final providers already tracked in `AGENTS.md`; they do not add platform implementations or USB work to this core repository.

- [ ] **Verify applicable CTAP 2.3 requirements command by command.** Check the implemented commands, extensions, error precedence and advertised capabilities against the [2026-02-26 Proposed Standard](https://fidoalliance.org/specs/fido-v2.3-ps-20260226/fido-client-to-authenticator-protocol-v2.3-ps-20260226.html). Start with ClientPIN/token lifecycle, then registration/assertions, credential management and Reset. Map requirements to existing native checks and add targeted cases for uncovered behavior. Keep only unresolved gaps here; do not claim full compliance from mock-provider tests.

- [ ] **Validate the final crypto providers against the documented contracts.** Verify SHA-256, HMAC-SHA-256, protocol-2 HKDF, AES-CBC, P-256 ECDH and ECDSA with independent known-answer/interoperability vectors. Exercise invalid peer coordinates, off-curve points, key-generation failure, RNG failure and UV/non-UV credential-secret separation. Confirm errors prevent token, credential or assertion publication. This is a release prerequisite dependent on provider availability, not a request to implement cryptographic primitives in the core.

- [ ] **Verify secret erasure and side-channel behavior with the production toolchain.** Inspect optimized code for `auth_secure_zero` and `ctap_pin_equal`; check provider implementations for secret-dependent branches/accesses in scalar, nonce, AES and HMAC operations. Exercise success and failure exits with instrumented providers to check cleanup of PIN plaintext, PIN verifiers, ECDH/HKDF intermediates and tokens, including provider-owned copies. Record target/compiler limitations and perform applicable target timing checks; source-level volatile writes alone are not evidence of complete hardware erasure or side-channel resistance.

- [ ] **Verify durable failure handling with the final storage/key providers.** Reuse the native failure scenarios, then inject interruptions around PIN retry writes, credential replacement/deletion, counter updates and combined Reset. After recovery, verify that retries cannot be restored by interruption, counters cannot roll back, abandoned staged keys are recovered, and successful Reset leaves no usable old credentials or PIN/token state. Coordinate this with the existing provider-validation work in `AGENTS.md`.

## 2. Best practices and resource safety

P2 below denotes finding severity, not the numbered review priority.

- [ ] **P2 — Reclaim inactive CTAPHID channel allocations.** `src/protocol/ctaphid_channels.c:ctaphid_channels_allocate` permanently consumes one of 16 slots per broadcast INIT; no release/eviction path exists. After 16 allocations, all subsequent clients receive ERR_OTHER until device reinitialization, even after every transaction has finished. Repeated normal client opens or an unauthenticated INIT burst can exhaust the device. Add bounded reclamation coordinated with transaction and continuation ownership; never evict an active channel or let a recycled slot inherit authorization. Extend the native channel/device checks to allocate more than 16 sequential clients and verify recovery and isolation. This concerns the portable coordinator, not a USB driver.

- [ ] **P2 — Bound command stack consumption before embedded integration.** `src/ctap/ctap_credential_management.c:ctap_credential_management_execute` keeps full credential records and request scratch on the stack, then calls `entry`, which allocates another record and a 1024-byte response. GCC `-O2 -fstack-usage` on the native x64 build reports 5,008 and 2,608 bytes respectively: 7,616 bytes for those two simultaneously live frames alone. Registration likewise nests `ctap_make_credential_finish_at` (2,240 bytes) and `auth_credentials_create_resident_prepared` (4,432 bytes), before attestation/provider calls. Move reusable large scratch into caller-owned per-instance storage, document the remaining stack requirement, and measure the complete worst-case call chain including CBOR recursion and providers with the target compiler. Add a build-time stack budget check. These are native measurements, not proof of an RP2350 overflow; the current core exposes no stack budget for integrators.

## 3. Junior readability

- [ ] **Make ClientPIN security transitions easier to audit.** In `src/ctap/ctap_client_pin.c`, separate dense checks and state mutations in `ctap_client_pin_execute` into clearly named stages or small helpers for retry persistence, PIN verification and token publication. Preserve error precedence, write ordering and the common secret-cleanup paths. Reuse `ctap_client_pin` and `ctap_conformance` checks; avoid a formatting-only rewrite.

- [ ] **Simplify backend command lifecycle handling.** In `src/protocol/ctaphid_ctap_backend.c`, centralize repeated pending-operation cleanup and separate command preparation, presence completion and response publication into readable helpers. Keep continuation snapshots distinct from per-operation state. Preserve CANCEL/INIT ownership checks and prevent duplicated side effects. Reuse the existing backend, presence, Reset and resident-credential tests.

- [ ] **Separate credential-management authorization from execution.** In `src/ctap/ctap_credential_management.c`, make subcommand parsing, MAC/scope validation, enumeration continuation and metadata mutation independently readable. Replace unexplained subcommand literals with local named constants where this clarifies authorization decisions. Preserve the exact authenticated parameter bytes and the checks preceding every storage mutation; reuse resident-credential and conformance tests.
